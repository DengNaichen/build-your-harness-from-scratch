# 03 · 超时到了，工具为什么还没返回

> 对应代码：当前 `src/host.ts` 的进程管理实现（修复前）　·　预计 40 分钟（含实验与实现练习）

## 问题

我们让 agent 帮忙查看 trace 网页，随后有一轮一直停在 `running`。
排查时发现：bash 工具有 120 秒的默认超时，也接了 Ctrl-C，
但这并不保证工具会按时返回。**发出了终止信号，不等于这次工具调用已经结束。**

原始记录停在 `2026-11-08T15-55-22-880/turn-011/req-003.json`。
它能证明前面的文件读取和端口检查已经完成，却没有记录第三次模型响应以及随后工具的开始、结束。
所以历史日志不能单独还原最后执行了什么。本课用一个独立实验，验证代码里确实存在的卡住机制。

我们要回答一个问题：**为什么 100ms 的超时，要等 2 秒才返回；如果那 2 秒换成一个一直运行的网页服务，会发生什么？**

## 实验

在仓库根目录运行，不需要 API key，也不会启动真实网页服务：

```bash
node lessons/03-process/timeout.ts
```

实验直接调用当前的 `createLocalHost().run()`，执行：

```bash
sleep 2 & wait
```

`sleep 2` 在后台运行，`wait` 让 bash 等待它。两个实验分别设置 100ms 超时、在 100ms 后 abort。
后代进程会在 2 秒后自行退出，因此实验不会留下常驻服务。

修复前应看到类似输出，实际耗时会有少量波动：

```text
--- timeout: 100ms; descendant lifetime: 2s ---
exit: signal
note: killed after 100ms timeout
--- stdout ---
(empty)
actual wait: 2034ms

--- abort after 100ms; descendant lifetime: 2s ---
error: AbortError
actual wait: 2010ms
```

这里最值得注意的是：结果声称 `killed after 100ms timeout`，但工具调用持续了约 2 秒。
这句提示描述的是定时器触发的时间，不是 Promise 返回的时间，也不能证明后代进程被清理了。

## 原因与最小修改

### 1. 先画出等待关系

当前 `src/host.ts` 用 `spawn("/bin/bash", ["-lc", command])` 启动命令。
在这个实验中，关系是：

```text
agent 的 runTurn
  └─ await tool.run()
       └─ await host.run()
            └─ bash -lc 'sleep 2 & wait'
                 └─ sleep 2
```

这是一条异步等待链。Node 的事件循环仍然可以处理定时器和信号，
但 agent 必须拿到工具结果，才能把它放进 transcript、请求模型继续下一步。
因此用户看到 agent 不动，不一定是 JavaScript 线程阻塞，也可能是等待的 Promise 始终没有结束。

### 2. 进程退出和输出管道关闭，是两件事

`spawn` 默认建立 stdout、stderr 管道。bash 启动的 `sleep` 继承了这些输出描述符。
虽然 `sleep` 不打印东西，但它仍然持有管道。

当前超时处理只有：

```ts
const timer = setTimeout(() => {
  killedForTimeout = true;
  child.kill("SIGKILL");
}, timeoutMs);
```

它针对的是直接启动的进程。终止 bash 不会自动把它启动的所有后代一起终止。

而 Promise 的完成条件放在这里：

```ts
child.on("close", (code) => {
  cleanup();
  if (killedForAbort) return reject(abortError());
  // 整理输出……
  resolve(parts.join("\n"));
});
```

需要区分两个事件：

| 事件 | 能说明什么 | 不能说明什么 |
|---|---|---|
| `exit` | 直接子进程已经退出 | stdout/stderr 已经关闭、后代已经退出 |
| `close` | 子进程结束，相关标准 IO 流已经关闭 | 所有脱离这些管道的后代也都已退出 |

100ms 时 bash 被杀掉，`sleep` 仍持有管道；约 2 秒时 `sleep` 退出，管道才关闭，
`close` 回调终于执行。**等待的最后一个条件是管道关闭，而不是 kill 已经调用。**

Ctrl-C 走的是同一条路径：设置标记、杀直接子进程、等 `close`，最后才抛 `AbortError`。
因此中断也会被拖住。

### 3. 为什么网页服务会把问题放大

像 `npm run view` 这样的命令可能形成 shell、npm、Node 服务组成的进程链。
具体中间层取决于 shell 如何执行命令，但服务本身的目标很明确：持续监听，直到被停止。

当前 bash 工具把所有命令都当成“最终会退出的工作”。这导致两个不同的问题：

1. 前台启动服务后，工具等待服务退出，agent 无法继续。
2. 到了超时时间，只杀中间进程，服务可能仍然活着并持有管道，工具继续等待。

单纯把超时加长不能解决这两个问题。把命令末尾加上 `&` 也不够：
后台进程仍可能继承输出管道，shell 退出后 `close` 依然等不到。

### 4. 实现练习：先让超时和取消可靠结束

**以下是待实现的修复要求，本文没有修改运行时代码。**
第一阶段只修 `Host.run` 的生命周期，保持现有工具接口和 transcript 契约。

在当前 macOS / POSIX 环境，可以为每次命令创建独立进程组：

```ts
const child = spawn("/bin/bash", ["-lc", command], {
  cwd: base,
  env: process.env,
  detached: true,
  stdio: ["ignore", "pipe", "pipe"],
});
```

这里 `detached: true` 用来建立独立的进程组，不代表工具可以立刻返回。
我们仍然需要收集输出、观察结束并清理资源。`stdin: ignore` 则明确这个工具不支持交互输入，
避免命令等待一个永远不会被写入的输入管道。

取消时向进程组发信号，核心操作形如：

```ts
if (child.pid !== undefined) process.kill(-child.pid, "SIGTERM");
```

负 PID 在这里表示进程组。普通后代会继承进程组，因此能一起收到信号。
这只是关键操作，不能直接当完整补丁：还要处理进程已经退出、重复取消和信号发送失败。
Windows 需要另外的实现；后代主动建立新会话也可能逃离该组。

建议把结束流程明确为：

```text
running
  ├─ 正常 close ───────────────────→ settled
  └─ timeout / abort → stopping
                        ├─ SIGTERM 发给进程组
                        ├─ 宽限期后仍未完成 → SIGKILL 发给进程组
                        └─ close 或最终收尾期限 → settled
```

实现时守住四件事：

- **Promise 只能结算一次。** `error`、`close`、超时、abort 会竞争；统一完成入口并清理定时器和监听器。
- **清理有自己的期限。** 如果升级信号后管道仍未关闭，最终兜底应停止收集并关闭本地管道，
  让调用返回，同时明确报告输出可能不完整、清理未获确认。不要再无限等待，也不要谎报全部进程已结束。
- **保留取消语义。** 用户中断仍抛 `AbortError`，让 `loop.ts` 给未回答的 tool call 补上中断结果。
  超时则沿用当前工具结果约定，明确标注超时并保留已收集的输出。
- **正常结束仍要收完输出。** 不要为了让实验变快，就直接把 `close` 换成 `exit`；那会丢掉尚未读完的输出，
  也不会解决后代进程残留。

第一阶段的修改落在 `src/host.ts` 和对应测试中。`loop.ts` 不需要知道进程组是什么，
也不应该为 bash 工具添加特判。

## 验证

修复后先重跑同一个实验：

```bash
node lessons/03-process/timeout.ts
```

两个调用都应该在取消阈值加上允许的清理时间内结束，不再等待 `sleep` 自然结束。
不要把恰好 100ms 当成断言：调度、启动 shell 和信号处理都需要时间。

自动化回归至少覆盖下面这些可观察行为：

| 场景 | 要证明的事情 |
|---|---|
| 普通命令输出后退出 | 输出完整，退出码正确 |
| shell 等待后代，发生超时 | 调用有界结束；受管理的后代也确实退出 |
| 同一场景发生 abort | 及时抛 `AbortError`，agent 能继续下一轮 |
| 后代忽略 SIGTERM | 宽限期后升级终止，不会永久等待 |
| 正常退出与取消同时发生 | 只结算一次，无未处理异常，无遗留定时器 |
| 调用前 signal 已经 aborted | 不启动进程，直接抛 `AbortError` |

测试不能只断言 Promise 返回得快。让实验后代把 PID 写入临时文件，再检查它退出，
并在测试的 `finally` 里兜底清理；否则“只提前 resolve，进程还活着”的错误实现也能过关。
时间断言留出合理余量，但必须明显短于测试后代的自然运行时间。

最后运行现有离线测试，尤其检查中断后的 transcript 不变量：

```bash
npm test
```

这些是完成修复的验收要求，不代表当前实现已经通过新增场景。

## 还没解决的：服务启动成功，不以进程退出为标准

修好超时后，前台执行 `npm run view` 的结果仍然会是：等待，超时，终止服务。
这说明取消能力修好了，但还没有满足“启动网页后，让 agent 继续工作”的需求。

常驻服务需要另一种生命周期：

| 操作 | 返回时意味着什么 |
|---|---|
| 启动 | 已创建受管理的后台会话，返回 session ID；尚不代表服务可用 |
| 检查就绪 | 在期限内访问预期的本地 HTTP 路径，确认服务可以响应，同时检查进程是否提前退出 |
| 读取输出 / 状态 | 按 session ID 查看新输出、运行状态和退出码 |
| 停止 | 终止对应进程组，返回清理结果 |

例如：启动 `npm run view` → 获取会话编号 → 检查 `http://127.0.0.1:4317` → 告知用户地址。
如果端口原本就有服务，还要结合本次进程状态和启动日志，避免把旧服务的响应误认为本次启动成功。

后台会话意味着 harness 要持续排空输出、限制日志占用，并规定自身退出时如何处理服务。
这些副作用仍应由 Host 管理。如果新增 Host 方法，需要按 `CONTRACTS.md` 显式记录接口迁移。
这一阶段不需要引入多线程或多个 agent；需要的是为仍在运行的进程保留一个可查询、可停止的身份。

最后，把观测补到出问题的位置：记录工具开始、结束、取消原因和耗时。
当前 trace 主要记录发给模型的请求，轮次结束时才更新状态；进程异常退出会留下 `running`。
网页不能仅凭这个字段断言 agent 仍然活着。要解释下一次卡住，日志必须能区分
“等模型”“执行工具”“正在清理”和“记录已中断”。
